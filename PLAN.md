# Jev – локален „decision engine“ (чеклист от край до край + статия)

Идея: вместо LLM да **генерира** текст, подаваме въпрос + фиксиран списък отговори и вземаме **вероятностно разпределение** върху тях от логитите на първия изходен токен. Без генериране, без JSON парсване.

## 1. Репо структура
```
lets-make-jev/
  PLAN.md
  jev/decide.py        # клиентът: prompt → token ids → /v1/score → решение
  jev/generate.py      # „стандартната“ лента през /v1/chat/completions
  data/*.jsonl         # support, candidate screening, expense review (по ~100 примера, с верен label)
  bench/run.py         # две паралелни ленти + barrier
  bench/results/       # JSON/CSV
  article/             # чернова, графики, скрийншоти
```

## 3. Ядро: `decide()`
- [ ] Choices = речник `{A: "billing", B: "technical_support", C: "account_access", D: "other"}`
- [ ] Prompt през chat template на модела, завършва точно на `Label:`
- [ ] **Валидация на токени:** за всеки етикет → `/tokenize` → трябва да е ТОЧНО 1 токен (внимавай `"A"` ≠ `" A"`, и за whitespace от шаблона)
- [ ] `POST /v1/score` с `query`, `items: []`, `label_token_ids`, `apply_softmax: true`
- [ ] Мапване обратно към смисъл (приложението вижда само `billing`, не `A`)
- [ ] **Escape отговор** (`other`/`escalate`) – иначе ограниченият softmax раздава вероятност на грешни опции
- [ ] Политика в кода: праг на top (напр. ≥0.80) и марж над втория (≥0.20), иначе → ръчна проверка
- [ ] Тест: 1 пример от край до край, сравни с ръчно изчислен softmax от логитите

## Бележки от коментарите (само смислените)
- [ ] **Batching:** `items` приема списък → N заявки в един `/v1/score`; за бенчмарка да тестваме и batched режим (споделен prefix на query)
- [ ] **Prompt-order bias:** подредбата на опциите влияе на предсказанието (твърдение: >7% флипове при размяна) и softmax-ът е некалибриран → тест: пермутирай реда на A/B/C и измери колко решения се менят; калибрация (напр. temperature scaling) върху dev сета
- [ ] **Escape route (OTHER/ESCALATE)** е ключов за production – вече в стъпка 3
- [ ] Не твърди „200× по-бърз / 400× по-евтин“ без собствени измервания (има скептичен коментар) – публикуваме само нашите числа
- [ ] Ограничение: работи само при затворено множество от отговори; при отворени въпроси – генериране
